# Journal · 工作旅程笔记

每项工作配一篇笔记：做的过程中随手记下想法、下一步、对代码的注解、做过的决定和走过的弯路；工作完成时写一段回顾并封存。以后翻开它，能看到当时是怎么一步步走过来的。git 记录了改了什么，journal 记录的是当时在想什么——这是它存在的理由。

## 一篇 journal 长什么样

文件在 `<项目根>/.journal/YYYY-MM-DD-<slug>.md`，脚本会自动定位项目根。

```markdown
---
title: 重构认证模块
status: active                 # 结束后变 closed
started: 2026-11-25 18:05
ended:
project: ~/maple
---

# 重构认证模块

## 目标
把 session 认证换成 JWT，为移动端铺路。

## 当前                          ← 活的区域：随时改写；结束时被「回顾」取代
**焦点**：拆 token 校验中间件
**下一步**
- [ ] 刷新 token 的过期策略
- [x] 写迁移脚本
**悬而未决**
- 旧 session 要不要双写一段时间？

## 旅程                          ← 只追加，不改写
> 💡想法 ➡️计划 📌注解 🔀决定 ⚠️问题 ✅进展 ↩️弯路 ❓疑问 🚩节点 🏁结束 · 〔名字〕= AI 补记
### 2026-11-25
- 18:05 🚩 开始：重构认证模块
- 18:20 💡 也许可以顺手把权限检查也抽成中间件
- 18:32 📌 `src/auth/token.ts:42` 过期判断用的是本地时间，跨时区会出问题
- 18:40 🔀 用 JWT，不再扩展 session —— 移动端没法稳定带 cookie 〔Claude〕
- 19:30 ↩️ 放弃用 Redis 存黑名单：为了登出引入 Redis 不划算，改成短过期 + 刷新
```

两个区域分工不同，这是整个设计的核心：

- **当前**回答「我现在在哪、接下来干什么」，服务于此刻和下次接着干。可以改写、勾掉、删掉。
- **旅程**回答「我是怎么走到这的」，服务于未来的回顾。只追加不改写——即使一个想法后来被证明是错的，也不要回头改它，而是新加一条 ↩️ 说明为什么放弃。被推翻的想法正是回顾时最有价值的部分。

## 工具脚本

`python3 __SKILL_DIR__/scripts/journal.py <命令>`（下文简写为 `journal.py`），在项目目录下运行。

| 命令 | 作用 |
|---|---|
| `new "标题" [--goal "目标"] [--slug en-slug]` | 新建，自动写入 🚩 开始；输出文件路径，可能附带 NOTE |
| `add <类型> "内容" [--by 名字] [-j 名称]` | 追加一条旅程（自动加时间和日期标题）；`next` 同时进入「下一步」，`question` 同时进入「悬而未决」 |
| `focus "内容"` | 改写「当前 · 焦点」 |
| `status [-n 10]` | 打印 目标 / 当前 / 最近 N 条旅程 |
| `close [--note "…"] < 回顾正文` | 用回顾替换「当前」，自动加历时、🏁 条目和 `status: closed` |
| `list [--active]` | 列出所有 journal |
| `hook` | 供 SessionStart hook 调用，平时不需要手动运行 |

类型：`idea` 💡想法 · `next` ➡️计划 · `note` 📌注解 · `decision` 🔀决定 · `issue` ⚠️问题/卡住 · `done` ✅进展 · `deadend` ↩️弯路/放弃 · `question` ❓疑问 · `flag` 🚩节点（暂停/继续等）

内容里有引号、反引号、`$` 或多行时，用 `-` 加 heredoc 从 stdin 传，避免 shell 转义出错：

```bash
python3 __SKILL_DIR__/scripts/journal.py add note - <<'EOF'
`src/auth/token.ts:42` 这里的 `exp` 是秒不是毫秒
EOF
```

只有一篇进行中时不需要 `-j`；有多篇时脚本会报错并列出它们，按上下文选一篇（文件名片段即可），拿不准就问用户。脚本只负责追加旅程和固定字段；勾掉「下一步」、整理「当前」这类改动直接编辑文件即可。

## 开始

用户说「开个笔记 / 开始记录 / 这个任务记一下过程」或 `/journal start …` 时：

1. 从对话上下文推一个简短标题和一两句目标。推不出目标就留着 `（待补充）`，不必为此打断用户。
2. 运行 `new`。输出里如果有 NOTE：
   - 另有进行中的 journal → 告诉用户，后续操作记得用 `-j` 指定。
   - `.journal/` 在 git 仓库里但没被处理 → 问用户一次：提交进仓库 / 只在本地忽略（写入 `.git/info/exclude`，不碰任何被跟踪的文件）/ 加进 `.gitignore`，然后照做。
3. 一句话告诉用户已开始，附上文件路径。

如果用户直接说「记一下…」但还没有进行中的 journal，按当前在做的工作推一个标题新建，告诉用户一声，然后记下这条。

## 记录

用户在工作中随口说的这些，都是 journal 的素材：

| 用户说的 | 类型 |
|---|---|
| 「突然想到…」「也许可以…」 | `idea` |
| 「下一步…」「回头还得…」「先记下，之后再弄」 | `next` |
| 「这里注意…」「这段代码其实是…」 | `note`（带上 `路径:行号`） |
| 「就这么定了」「还是用 X 吧」 | `decision`（带上为什么） |
| 「卡住了」「这个 bug 好怪」 | `issue` |
| 「X 搞定了」 | `done`（如果对应某条下一步，顺手在「当前」把它勾成 `[x]`） |
| 「这条路走不通」「算了不这么做了」 | `deadend`（带上为什么） |
| 「不确定…」「还没想清楚…」 | `question`（解决后在「当前」删掉它，并记一条说明怎么解决的） |

怎么写：

- **保留用户的原话和语气**，只做轻微整理（去掉口头禅、补全「这个」「那里」指的是什么）。半成品的想法就该是半成品的样子；润色成报告腔，未来的自己反而读不出当时的状态。
- **一条一个念头**。用户一句话里既有想法又有计划，就拆成两条。
- **决定和弯路一定写上「为什么」**。做了什么 git 会记得；为什么这么做、为什么放弃，几周后最先忘掉的就是它们。
- **注解带上位置**，如 `` `src/auth/token.ts:42` ``，回顾时能直接跳过去。
- 焦点明显转移时（比如从写功能转到排查 bug），用 `focus` 更新。

记完只用很短的一句确认（如「已记 💡」），不要把内容复述一遍。如果用户的消息一半是要记的东西、一半是编码任务，记完就继续做任务——journal 是工作的副产品，不应该打断工作。

### AI 补记

journal 进行中时，你也可以在关键节点主动补一条，加 `--by <你的名字>`（如 `--by Claude`、`--by Codex`），条目末尾会带上〔名字〕，回顾时能分清哪些是用户的原话、哪些是 AI 的旁白。值得补记的：

- 和用户一起拍板的决定，以及理由
- 查到的根因、对代码或系统的非显然发现
- 尝试后放弃的方案，以及为什么
- 方向上的转变

不值得补记的：例行的改动、命令输出、git diff/log 本身就能看到的东西。

保持稀疏，一次会话通常几条就够。这是用户的思考空间，AI 的补记是旁白，不能喧宾夺主。补记后在回复末尾用一行轻轻提一下（如「（已补记 🔀 选用 JWT 的原因）」），让用户知道发生了什么，不满意可以删。

## 继续

如果会话开头的上下文里有一段 `[journal] …` 提示（来自 SessionStart hook），说明当前项目有进行中的 journal：不必主动汇报，但从这时起，用户提到的想法、计划、决定都按上面的方式记录。

新会话里接着干、或用户问「做到哪了 / 继续上次的」时：运行 `status`，用三五行告诉用户当前焦点、没勾掉的下一步、悬而未决的问题、上次最后做到哪。如果是隔了一段时间重新开工，加一条 `flag "继续：…"`，这样回顾时能看出工作的节奏。

## 结束

用户说「做完了 / 收尾 / 结束这个 journal」，或者「这个不做了」时：

1. 读完整篇 journal（`status -n 0` 或直接读文件），结合本次会话的上下文。
2. 写回顾正文，结构如下。不要写「## 回顾」标题和历时，脚本会加：

   ```markdown
   **结果**：对照「目标」，做成了什么、没做成什么。中途放弃的也照实写。

   **关键决定**
   - 决定 —— 当时的理由（11-25 18:40）

   **弯路与发现**
   - 试过什么、为什么放弃；发现了什么意料之外的事

   **遗留**
   - [ ] 没勾掉的下一步、没解决的疑问，原样带过来——将来接着做时从这里起步

   **给未来的自己**：一两句话。
   ```

   回顾里的每一条都应该能在旅程或会话里找到依据，不要编造没发生过的细节。旅程很短，回顾就短；某一栏没内容就省掉。
3. 用 heredoc 把回顾正文传给 `close`（用户放弃时可加 `--note "中止：原因"`）。
4. 告诉用户已结束，给一句话总结和文件路径。「给未来的自己」是你代拟的，邀请用户换成自己的话（直接改文件即可）。

结束后的 journal 是历史记录，不要再改它的「目标」「回顾」「旅程」。用户之后有新感想，在文末追加 `## 后记`，带上日期。如果之后要接着做同一件事，新开一篇，在「目标」里链接旧的那篇（如 `接续 [重构认证模块](2026-11-25-重构认证模块.md)`），让旅程连起来。

## 回顾

- **「我都记过哪些」**：运行 `list`。
- **回顾某一篇**：读全文，讲一个故事而不是复述文件：起点和目标 → 关键转折（决定、弯路、卡住的地方）→ 结果 → 留下了什么，并引用时间点。重点放在被推翻的想法和方向变化上，这些是记忆最容易抹平的部分。
- **带着问题回顾**（「当时为什么选 JWT」「那个时区 bug 后来怎么解决的」）：在 `.journal/` 里 grep 关键词（可配合类型 emoji，如 `🔀` 找决定、`↩️` 找弯路），引用原条目和时间回答。
- **跨篇回顾**（「这个月做了什么」「最近踩过哪些坑」）：`list` 后读相关几篇的「回顾」区块，必要时再看旅程，归纳出共同的模式。

回顾时只读不写，除非用户要求追加后记。
